# 已知限制

本頁只描述目前程式已確認的邊界，不把部分驗證寫成完整相容保證。

## 1. 大型文字輸入

- `128000` 個 UTF-16 碼元是預設的 Web 相容政策；超過此設定的實際 caller outbound text 會由 Sidecar 拒絕。
- 這個數字不是 token context window，也不應直接當成 Agent 的 `context_length`。Sidecar 會先完成 checkpoint/delta 整理，再對實際要送往 ChatHub 的 caller text 套用此政策，避免把呼叫端重送的舊歷史錯算成新的 outbound delta。
- Microsoft 後端可能接受更大的直接輸入，但處理時間與成功率沒有穩定保證。
- 「後端接受請求」不等於「能在合理時間內完成」；外層反向代理 timeout 也可能先終止長任務。部署原則請見 [部署與反向代理](部署與反向代理.md)。Hermes 的 provider/model context 設定請見 [Hermes 整合指南](Hermes整合指南.md)。

## 2. 大型工具結果

- 大型工具結果仍有被上游壓縮或截短的風險。
- 若呼叫端要求逐位元組保留大型工具輸出，必須先以實際負載驗證，不應只依賴一般文字與小型工具測試。

## 3. 同一輪的多個呼叫端工具

- 呼叫端通常可以解析多筆 `tool_calls`，但 Sidecar 尚未對同一個 assistant turn 產生多個獨立呼叫端工具提供完整端對端保證。
- 需要 `parallel_tool_calls` 時，應先針對目標模型與呼叫端進行實測。

## 4. Bing 與呼叫端工具混用

- 原生 Bing 並非必然與呼叫端工具衝突。
- 實際路由高度依賴工具提示詞；過度限制的文字可能讓模型只選呼叫端工具而不使用 Bing。
- 發生衝突時應先檢查提示詞契約，不要先移除 Bing 或另造搜尋工具。

## 5. Code Interpreter 產出檔案

- Sidecar 已實作帶認證的上游擷取與產出檔案物化，不會把瀏覽器 `blob:` URL 或受保護的 Microsoft 暫時網址直接交給呼叫端。
- 成功擷取後，檔案會存入本機私有儲存區並回傳短期下載網址（capability URL）；網址的持有者即可下載，預設有效期為 24 小時，因此必須視同短期憑證保護。
- 遠端提供下載連結時必須設定正確的 `M365_PUBLIC_ORIGIN`，且 loopback 以外只接受 HTTPS。
- 若上游認證、檔案完整性或本機容量檢查失敗，物化流程會失敗關閉，不會退回受保護的上游網址。

## 6. Private 模式的隱私邊界

- `disableMemory=1` 可避免一般聊天歷史，但不代表 Microsoft 完全不保留資料。
- 文件與圖片走不同的傳輸路徑；一般文件仍可能在 OneDrive 或 SharePoint 建立暫存副本。
- 對外說明不應把 Private 模式簡化成「零保留」。

## 7. MCP 可用性

- `/v1/mcp`、`/v1/mcp/sse` 與 `/v1/mcp/message` 均已掛載，並要求有效的 Bearer API 金鑰。
- `/v1/mcp` 使用 Streamable HTTP；後兩者是成對的舊版 SSE 傳輸。呼叫端必須支援所選傳輸與 MCP 初始化流程。
- 目前內建 provider 只提供 `wp6_echo` 互通驗證工具；這些路由不是任意外部 MCP server 的自動登錄中心。

## 8. 上游關係

- 公開 `gpxsrz/M365-Copilot2API` 的 `main` 是本專案唯一開發主線。
- `HEXUXIU/M365-Copilot2API` 僅供唯讀比較，不承諾自動同步或功能完全一致。
- 若要匯入上游變更，必須先逐項檢查差異與本專案測試，再透過公開主線整合。

## 9. 容器首次啟動

- `Dockerfile` 可建置非 root 容器映像，但一般 bridge/NAT 不會讓容器內收到真正的 loopback 管理請求。
- 一次性 bootstrap secret 在非 loopback 管理介面會被安全策略拒絕，因此本專案不提供未經驗證的通用 Compose 快速啟動。
- 容器部署必須自行處理 HTTPS、可信反向代理、資料卷擁有權與持久管理員密碼；不得以放寬管理介面安全檢查作為捷徑。

## 10. Hermes / Hindsight 共用帳號吞吐量

- Hermes 與 Hindsight 可以使用彼此隔離的相容入口與 checkpoint 邊界，同時共用同一個 Microsoft 365 帳號；Hermes 專用 chat 使用 `hermes` namespace，Memory chat 則不建立 Sidecar continuation checkpoint。
- 兩者仍共用帳號級 ChatHub 吞吐量，因此 Hindsight 背景整理可能和 Hermes 在同一時間遇到延遲或 throttling。
- Sidecar 對新的 Memory 工作做 cooperative admission control：互動式 `/v1/chat/completions` 與 `/hermes/v1/*` 流量優先，Memory 採 FIFO 排隊；已經在執行的 Memory 不會被搶占。
- 真實 Microsoft 帳號不得用高併發故意觸發 429。限流、SSE 429 logical outcome 與退避行為以本地 deterministic test 驗證，線上維持低併發。

# Known Limitations

This page documents confirmed boundaries only. Partial validation is not presented as a complete compatibility guarantee.

## 1. Large text input

- `128000` UTF-16 code units is the default web-compatible policy. Caller text above that configured limit is rejected by the sidecar.
- The Microsoft backend may accept larger direct input, but latency and completion reliability are not guaranteed.
- Backend acceptance does not mean a request will complete in a reasonable amount of time.

## 2. Large tool results

- Large caller-tool results may still be compressed or truncated upstream.
- If byte-for-byte preservation of a large tool result matters, validate the actual workload instead of extrapolating from ordinary text or small tool tests.

## 3. Multiple caller tools in one turn

- Consumers can generally parse multiple `tool_calls`, but the sidecar does not yet claim complete end-to-end support for several independent caller tools emitted in one assistant turn.
- Validate `parallel_tool_calls` with the target model and consumer before depending on it.

## 4. Bing mixed with caller tools

- Native Bing is not inherently incompatible with caller tools.
- Routing is highly sensitive to tool-prompt wording; overly restrictive instructions can suppress Bing.
- Check the prompt contract before removing Bing or inventing a replacement search tool.

## 5. Code Interpreter artifacts

- The sidecar fetches protected upstream artifacts with authenticated Microsoft state and materializes them into private local storage rather than exposing browser `blob:` URLs or protected Microsoft temporary URLs.
- Successful materialization returns a short-lived capability URL. Possession of that URL grants download access, so treat it as a temporary credential. The default lifetime is 24 hours.
- Remote download links require a correct `M365_PUBLIC_ORIGIN`; non-loopback origins must use HTTPS.
- Upstream authentication, integrity, or local-capacity failures fail closed and never fall back to protected upstream URLs.

## 6. Private-mode privacy boundary

- `disableMemory=1` prevents ordinary chat history but does not imply zero Microsoft retention.
- Documents and images use different transport paths; ordinary documents may still create OneDrive or SharePoint staging copies.
- Public descriptions should not simplify Private mode to “zero retention.”

## 7. MCP availability

- `/v1/mcp`, `/v1/mcp/sse`, and `/v1/mcp/message` are mounted and require a valid Bearer API key.
- `/v1/mcp` uses Streamable HTTP; the other two form the legacy SSE transport. Consumers must support the selected transport and MCP initialization flow.
- The built-in provider currently exposes `wp6_echo` for interoperability validation. These routes are not an automatic registry for arbitrary external MCP servers.

## 8. Upstream relationship

- Public `gpxsrz/M365-Copilot2API` `main` is the single development line.
- `HEXUXIU/M365-Copilot2API` is read-only reference material; automatic synchronization and complete parity are not promised.
- Upstream changes must be reviewed individually and integrated through the public mainline with project tests.

## 9. First container startup

- The `Dockerfile` builds a non-root image, but ordinary bridge/NAT networking does not make management requests appear as true loopback traffic.
- The one-time bootstrap secret is intentionally rejected on non-loopback management surfaces, so the project does not provide an unverified universal Compose shortcut.
- Container deployments must provide HTTPS, trusted reverse proxy configuration, correct volume ownership, and a persistent administrator password without weakening management security checks.

## 10. Hermes / Hindsight shared account throughput

- Hermes and Hindsight can use isolated compatibility endpoints and checkpoint boundaries while sharing the same Microsoft account; dedicated Hermes chat uses the `hermes` namespace, while Memory chat does not create a sidecar continuation checkpoint.
- They still share account-level ChatHub throughput. Hindsight background work can therefore increase latency or encounter throttling at the same time as Hermes.
- The sidecar gives interactive `/v1/chat/completions` and `/hermes/v1/chat/completions` traffic priority over new Memory work and exposes Memory concurrency, queue timeout, interactive holdoff, and 429 backoff controls. Memory admission is FIFO. This is cooperative admission control, not preemption: Memory work already in flight is allowed to finish.
- Real Microsoft accounts must not be deliberately flooded to force 429 responses. Rate-limit behavior is validated locally; live verification remains low-concurrency.
