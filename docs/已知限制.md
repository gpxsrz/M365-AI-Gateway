# 已知限制

本頁列出公開快照目前應誠實揭露的限制與風險，避免把「已有部分證據」誤說成「全線完成」。

## 1. 大型文字輸入

- `128000` UTF-16 units 是保守且已驗證的 Web-compatible policy。
- 更大的 direct ChatHub 輸入可能被接受，但完成時間顯著增加。
- 因此「成功送出」與「合理時間內完成」必須分開看待。

## 2. Large tool result

- 現有快照仍有大型 tool result 被壓縮或截短的風險。
- 若上層 consumer 依賴完整的大型 tool output，必須先補完這條路徑，再宣稱相容。

## 3. 同 turn 多 caller tools

- consumer 端通常可以理解多筆 `tool_calls`，但此快照不應直接宣稱 Sidecar 已完整支援在同一 assistant turn 產生多個獨立 caller tools。
- 若需求是 `parallel_tool_calls` 的完整端對端保證，仍需額外驗證。

## 4. Bing 與 caller tool 混用

- native Bing 並不是天生與 caller tools 衝突。
- 目前真正的不穩定點是 tool-routing prompt wording；過度限制的 prompt 會讓模型只做 caller tool，進而壓制 Bing。
- 因此修正方向應先看 prompt contract，而不是先刪除 Bing 或重造一個假的 web-search tool。

## 5. Code Interpreter artifact 回傳

- 上游 artifact 下載需要 authenticated artifact fetch。
- 瀏覽器 `blob:` URL 不是可直接跨 client 使用的 API 結果。
- 在 authenticated fetch 沒有補完前，只能說「上游會產生 artifact」，不能說「consumer 已可穩定下載 artifact」。

## 6. Private mode 的隱私邊界

- `disableMemory=1` 對 no-ordinary-history 很重要，但不代表 Microsoft 完全不保留資料。
- 一般文件上傳仍可能在 OneDrive / SharePoint 建立 staging copy。
- 因此對外說明時應避免把 private mode 簡化成「零保留」。

## 7. MCP 可用性

- 程式中有 modern / legacy MCP 實作，不等於每個 consumer 都能立即用上。
- 若某個 consumer 需要特定 `MCP` 路徑，例如 legacy SSE route，仍要確認 production router 是否真的掛載。

## 8. 衍生快照範圍

- 這個公開樹是維護者整理的參考快照，不承諾追上所有較新的上游功能。
- 若你需要最新上游特性，應自行比對上游目前狀態，而不是假設此快照會持續同步。
