# 研究與測試成果

本文件整理目前公開 `main` 的實作與驗證結論，供實作者理解行為邊界；內容不含私人路徑、帳號識別、原始封包或內部治理資訊。

## 1. 文字輸入與 checkpoint 行為

- `128000` UTF-16 units 是官方 Web editor 的已驗證相容邊界：`128000` 可送出，`128001` 由 UI 阻擋。
- 這個數值**不是**目前已證明的 ChatHub backend 硬上限。較大的 direct ChatHub 輸入曾成功通過 transport 並取得 backend acceptance。
- 對外公開時，最安全的產品說法是：
  - `128000` 為 Web-compatible policy。
  - 更大的輸入可能被接受，但處理時間會明顯增加，也可能因排程或模型執行時間而 timeout。
- Conversation reuse 應依 strict hash-prefix / checkpoint ordering 驗證：
  - 只有在舊 history 前綴完全一致時才沿用既有 Microsoft `ConversationId`。
  - 若上層 consumer 改寫了歷史訊息、壓縮了舊內容，或 tool result 內容不同，就應安全地建立新 conversation，而不是做 fuzzy match。

## 2. Private / Temporary Chat 與記憶邊界

- `disableMemory=1` 是目前最重要的 no-ordinary-history transport control。
- 同一個 Private / Temporary conversation 內，Microsoft 仍可能保留短期 continuation state；這不等於長期 memory。
- 因此合理責任分工是：

```text
長期 history / memory / compression
→ 由上層 consumer 管理

短期 ConversationId / SessionId / file continuation
→ 由 Sidecar 只在當前流程內短暫使用
```

- 重新建立 ChatHub WebSocket 時，應再次套用 `disableMemory=1`；不能因為沿用同一個 `ConversationId` 就假設 private policy 仍自動有效。

## 3. Files、圖片與多模態行為

### 一般文件

- 一般文件不是把原始 bytes 直接塞進 ChatHub `message.text`。
- 目前可公開描述的實作方向是：

```text
Graph createUploadSession
→ SharePoint / OneDrive upload
→ file identity / annotation
→ ChatHub grounding
```

- 文件上傳與聊天 no-history 是兩個不同問題。即使使用 `disableMemory=1`，文件仍可能在 Microsoft 端建立 staging copy。
- 同一 turn 的 active attachments 以 3 個為已驗證上限；文件與圖片共用這個配額。

### 圖片與 Vision

- 圖片與一般文件走不同 transport。
- Vision 已有單圖、多圖、不同圖片格式的正向驗證；圖片內容會真正進入模型處理，而不是只經過本地假解析。
- 圖片路徑不應強迫共用文件的 Graph / SharePoint upload flow。

## 4. Bing、caller tools 與工具協調

- `tools` schema 的存在，本身不代表 Microsoft native Bing 一定會被關閉。
- 已觀察到的主要風險是 tool-routing prompt wording：
  - 若 prompt 把模型限制成「只能先處理 caller tool」，native Bing 可能被壓制。
  - 若 prompt 明確保留 Microsoft native Bing / citations / grounding，則 Bing 與 caller tool 可以在同一 turn 共存。
- 這代表問題更像是 prompt / routing contract，而不是 upstream 完全不支援 coexistence。

## 5. Code Interpreter 與產出檔案

- `Code Interpreter` 可在上游真正執行 Python，並回傳 output-file metadata。
- 瀏覽器中可點擊的 `blob:` URL 只是前端表現層，不是可直接交給 API 呼叫端的上游檔案 identity。
- Sidecar 已完成下列物化路徑：

```text
以已登入身分擷取上游檔案
→ 本機私有儲存區
→ 短期 capability URL
```

- capability URL 的持有者即可下載，因此必須視同短期憑證保護；上游擷取、完整性或容量檢查失敗時會失敗關閉。

## 6. SignalR terminal semantics

- ChatHub stream 的 partial update 不能單獨當作成功完成。
- 公開 API 相容層應以 terminal completion 為準，再決定是否輸出最終 `finish_reason`、usage 與 `data: [DONE]`。
- 對 SSE consumer 而言，重點不是只看到零散 delta，而是：
  - partial deltas 順序正確；
  - terminal completion 到達；
  - 最後補上 `[DONE]`。

## 7. MCP 與 Hermes 呼叫端相容性

- `/v1/mcp`、`/v1/mcp/sse` 與 `/v1/mcp/message` 均已掛載；第一條使用 Streamable HTTP，後兩條是成對的舊版 SSE 傳輸。
- 路由已掛載不等於每個呼叫端都能直接互通；實際相容性仍取決於呼叫端支援的傳輸與 MCP 初始化流程。
- Hermes 正式整合應優先使用 `POST /hermes/v1/chat/completions`；一般 `/v1/chat/completions` 保留向後相容與其他 OpenAI-compatible caller 使用。MCP、artifact 與其他既有通用能力仍維持 `/v1/*`。
- 文字、SSE 串流、單一呼叫端工具、視覺輸入、一般續接與短期產出檔案下載已有正向證據。#42 已把多工具上限改成「模型生成前固定」：只有所有可選工具明確 read-only 才可大於 1，其他 catalog 事前序列化成 1；不再模型回 2 個後才改成 1，也不截斷部分 tool state。Production 以兩個未帶 `readOnlyHint` 的 Hermes tools 實測第一輪只回 1 個 `read_file`，第二輪同 session/tool result 正常續接並 `stop`；多個明確 read-only tool 與 Bing 混用仍應依目標 workload 額外驗證。

## 8. Hermes 與 Hindsight 相容模式

- `GET /hermes/v1/models` 與 `POST /hermes/v1/chat/completions` 是 Hermes 專用 models/chat 入口；chat 使用獨立 `hermes` checkpoint namespace。MCP、artifact 與其他通用能力仍維持既有 `/v1/*` 路徑。
- `GET /memory/v1/models` 與 `POST /memory/v1/chat/completions` 是 Hindsight／Memory Provider 專用 models/chat 入口；memory chat 不建立 Sidecar continuation checkpoint，並強制清空 caller 帶入的 conversation/session 綁定，讓每個 memory 工作使用新的 ChatHub conversation。
- Hindsight structured output 由 Sidecar 加強 JSON Schema contract：先明確提示 schema，若第一次候選不合格，只允許有界修復並再次本地驗證，不以固定模型名稱作為相容前提。
- #43 讓 `/memory/v1` caller-text overflow 回 Hindsight 可辨識的 HTTP 400 `context_length_exceeded` + `input is too long`，同時用 metadata 明確保留真正的 UTF-16 transport policy。唯讀檢查 Hindsight 0.9.0 顯示 Reflect 可據此停止 agent loop 並轉 final synthesis；Production 最終只靠設定將 Reflect `max_context_tokens` 調成 `40000`、Reflect retry 調成 `1`，不修改 Hindsight core。retry `0` canary 曾把一次 ChatHub WebSocket handshake 500（M365 502）直接放大成 Hindsight reflect 500；改成 `1` 後，deterministic 400 最多只多重送一次，同時保留一次 transient retry，且臨時 bank retain → recall → reflect 真實驗證成功後已刪除測試資料。
- #44 對一般 `/v1/chat/completions`、`/v1/responses`、`/v1/messages` 保留 `text_policy_exceeded`，並附 `caller_text_utf16` limit/received/reduction-and-retry metadata，不把 128K UTF-16 冒充成 128K model tokens。三個入口均已在 Production 以 128001 UTF-16 caller text 驗證相同 recovery contract。
- #49 將跨 turn 的 tool-round 安全上限改成 consumer profile：一般 `/v1` 與 Memory 維持 16，Hermes `/hermes/v1` 使用可獨立調整的 128。Deterministic HTTP tests 證明 Hermes 在 16→17 可繼續並保留 checkpoint/tool identity；generic、Memory、Responses、Anthropic 仍在 16 terminal；Hermes 到 128 則仍以 machine-readable `tool_round_limit` 終止 runaway loop，不自動 replay。
- #54 移除 model-tool-router repair prompt 原本固定 6000 字元的 compact：streaming / non-streaming deterministic tests 證明 malformed outer JSON 進入 bounded repair 時會保留完整 structured arguments，完整 repair input 若超過 `textInputLimitUTF16` 則在第二次 upstream call 前以 `tool_router_repair_input_too_large` fail closed，不再截斷 arguments。Production Hermes canary 實際成功執行超過 13K 字元、保留中段 sentinel 的 `execute_code` arguments；該 live canary 本身沒有進入 repair，因此它證明大型 arguments transport，repair losslessness 則由 deterministic tests 覆蓋。canary 中模型自行改寫了 prompt padding，所以這項保證不等於「使用者 prompt 與最終 tool arguments 逐位元組相同」。
- #57 修正 final-answer path 再次回出 internal `{"calls":[],"answer":"..."}` 時的 envelope 外漏。共用 OpenAI chat 邊界只解開完整且明確的 direct-answer envelope；ordinary JSON 不動，non-empty calls 或 ambiguous router-like JSON fail closed，malformed JSON 不猜測式剝殼。Generic `/v1`、Hermes `/hermes/v1`、Memory `/memory/v1` 的 stream/non-stream 六條 Production canary 全部通過，Memory JSON Schema 另有 live 驗證。
- Hermes 2026-08-12 canary 曾將 M365 model-specific `context_length` 調為 `80000`、`proactive_prune_tokens` 調為 `41000`，全域 `compression.threshold_tokens` 維持未設定；實際 oneshot terminal tool turn 完成 2 次 API call，Hermes 原生 `ContextCompressor` 亦驗證 40999 不 prune、41000 會開始 deterministic old-tool-result prune。2026-08-13 的真實 tool-heavy 長任務進一步證明 80K 對 `128000 UTF-16` transport policy 不夠保守：多次壓縮到約 49K–52K rough tokens 後，新增 tool results 仍可反覆撐破 transport limit 並耗盡 3 次 compression recovery。因此目前 Production 基線改為 `context_length=64000`、`proactive_prune_tokens=41000`、`max_attempts=3`、`protect_last_n=20`；80K 歷史 canary 保留為「曾可用」，不再是現行建議值。
- 實測繁中 retain / recall / reflect 可正常運作。矛盾舊事實可能在 retain 後短暫與新事實並存，但 consolidation 完成後可整理成最新狀態；因此 production 需監控 consolidation 是否 pending/failed。
- Hermes 與 Hindsight 可以共用同一 Microsoft 365 帳號，但共用帳號級吞吐量。M365-Copilot2API 對新 Memory 工作實作 admission control：既有 `/v1/chat/completions` 與專用 `/hermes/v1/*` 都視為互動式流量，會讓新的 Memory 工作暫緩進場；Memory 採 FIFO 排隊，已在執行的 Memory 不被中斷。
- 429/backoff 行為以本地 deterministic test 驗證；不使用高併發實機測試刻意把 Microsoft 帳號打到 429。

# Research and Validation Results

This document summarizes implementation and validation conclusions from the current public `main` without exposing private paths, account identifiers, raw packets, or internal governance data.

## 1. Text input and checkpoint behavior

- `128000` UTF-16 units is a verified compatibility boundary of the official web editor: `128000` can be submitted, while the UI blocks `128001`.
- It is **not** a proven hard limit of the ChatHub backend. Larger direct ChatHub inputs have reached backend acceptance in testing.
- The safest public statement is that `128000` is the web-compatible policy; larger values may work but can take much longer and may time out.
- Conversation reuse follows strict hash-prefix / checkpoint ordering. If a consumer rewrites, compresses, or changes old history or tool results, a fresh upstream conversation should be created instead of using fuzzy matching.

## 2. Private / Temporary Chat and memory boundary

- `disableMemory=1` is the main no-ordinary-history transport control.
- Microsoft may still retain short-lived continuation state inside a Private / Temporary conversation; that is not the same as long-term memory.
- Long-term history, memory, and compression belong to the consumer; short-lived `ConversationId`, `SessionId`, and file continuation belong to the sidecar transport flow.
- `disableMemory=1` must be reapplied whenever a ChatHub WebSocket is recreated.

## 3. Files, images, and multimodal behavior

- Ordinary documents are not inserted as raw bytes into ChatHub message text. The public implementation model is Graph upload session → SharePoint / OneDrive upload → Microsoft file identity / annotation → ChatHub grounding.
- No-history chat and document upload are separate boundaries; document staging copies may still exist on Microsoft storage.
- Three active attachments per turn is the verified quota shared by documents and images.
- Images use a different transport from ordinary files. Single-image and multi-image Vision paths have positive evidence.

## 4. Bing, caller tools, and routing

- The presence of a `tools` schema does not inherently disable native Bing.
- Tool-routing prompt wording is the main observed risk: overly restrictive instructions can suppress Bing, while preserving native Bing/citations/grounding in the contract allows coexistence.
- This behaves more like a prompt/routing-contract problem than an upstream impossibility.

## 5. Code Interpreter and artifacts

- Code Interpreter can execute Python upstream and return output-file metadata.
- Browser `blob:` URLs are presentation-layer artifacts, not API-safe upstream file identities.
- The sidecar materializes artifacts by authenticated upstream fetch → private local storage → short-lived capability URL.
- Capability URLs must be protected like temporary credentials; authentication, integrity, or capacity failures fail closed.

## 6. SignalR terminal semantics

- Partial ChatHub updates are not sufficient evidence of successful completion.
- The compatibility layer waits for terminal completion before final `finish_reason`, usage, and `data: [DONE]` behavior is considered successful.
- Correct SSE behavior means ordered partial deltas, terminal completion, and a final `[DONE]`.

## 7. MCP and Hermes consumer compatibility

- `/v1/mcp`, `/v1/mcp/sse`, and `/v1/mcp/message` are mounted; the first is Streamable HTTP and the latter two form the legacy SSE transport.
- Mounted routes do not imply automatic compatibility with every consumer; the selected MCP transport and initialization flow still matter.
- Hermes production integration should prefer `POST /hermes/v1/chat/completions`; generic `/v1/chat/completions` remains backward-compatible for other OpenAI-compatible consumers, while MCP/artifact capabilities stay on established `/v1/*` routes.
- Text, SSE streaming, one caller tool, Vision, ordinary continuation, and short-lived artifact download have positive Hermes evidence. #42 fixes the multi-tool ceiling before model generation: limits above 1 require all selectable tools to be explicitly read-only, otherwise the turn is serialized to 1. It no longer downgrades from 2 to 1 after generation or truncates part of the tool state. In Production, a Hermes request exposing two tools without `readOnlyHint` emitted exactly one `read_file` call and continued normally with the same session/tool result to `stop`; multiple explicitly read-only tools and Bing-mixed routing should still be qualified for their target workload.

## 8. Hermes and Hindsight compatibility profiles

- `GET /hermes/v1/models` and `POST /hermes/v1/chat/completions` are the Hermes-specific models/chat surface; chat uses the isolated `hermes` checkpoint namespace. MCP, artifact, and other general capabilities remain on the established `/v1/*` routes.
- `GET /memory/v1/models` and `POST /memory/v1/chat/completions` are the Hindsight / Memory Provider models/chat surface; memory chat bypasses sidecar continuation checkpoints and clears caller-supplied conversation/session bindings so every memory job starts a fresh ChatHub conversation.
- Hindsight structured output receives an enhanced JSON Schema contract in the sidecar. Invalid first candidates may receive one bounded repair and must still pass local schema validation. Compatibility does not depend on pinning one specific model name.
- #43 maps `/memory/v1` caller-text overflow to Hindsight-recognizable HTTP 400 `context_length_exceeded` plus `input is too long`, while metadata still identifies the real UTF-16 transport policy. Read-only inspection of Hindsight 0.9.0 shows that Reflect can stop its agent loop and move to final synthesis on that signal. Production finally uses Reflect-specific `max_context_tokens=40000` and retry `1` without Hindsight core changes. A retry-`0` canary turned one ChatHub WebSocket handshake 500 (M365 502) into an immediate Hindsight reflect 500; retry `1` bounds deterministic 400 duplication to one extra attempt while preserving one transient retry, and a temporary bank then completed retain → recall → reflect successfully and was deleted after the test.
- #44 keeps `text_policy_exceeded` for generic `/v1/chat/completions`, `/v1/responses`, and `/v1/messages` and adds `caller_text_utf16` limit/received/reduction-and-retry metadata instead of pretending the 128K UTF-16 policy is a 128K-token model context window. All three generic surfaces passed Production verification with 128001 UTF-16 caller text.
- #49 makes the cross-turn tool-round safety ceiling consumer-specific: generic `/v1` and Memory remain at 16 while `/hermes/v1` receives an independently configurable default of 128. Deterministic HTTP tests prove Hermes can continue from round 16 to 17 while preserving checkpoint/tool identity; generic, Memory, Responses, and Anthropic remain terminal at 16; Hermes still terminates a runaway loop at 128 with machine-readable `tool_round_limit` metadata and no automatic replay.
- #54 removes the model-tool-router repair prompt's former fixed 6000-character compaction. Streaming and non-streaming deterministic tests prove that malformed outer JSON entering bounded repair preserves complete structured arguments; if the complete repair input exceeds `textInputLimitUTF16`, the sidecar fails closed before a second upstream call with `tool_router_repair_input_too_large` instead of truncating arguments. A Production Hermes canary successfully executed more than 13K characters of `execute_code` arguments with a middle sentinel intact. The live canary itself did not enter repair, so it proves large-argument transport while deterministic tests establish repair losslessness. The model rewrote the prompt padding in that canary, so this guarantee does not mean byte-for-byte identity between user-prompt code and final tool arguments.
- #57 fixes leakage when the final-answer path returns the internal `{"calls":[],"answer":"..."}` envelope again. The shared OpenAI-chat boundary unwraps only a complete, unambiguous direct-answer envelope; ordinary JSON is preserved, non-empty calls or ambiguous router-like JSON fails closed, and malformed JSON is not heuristically stripped. All six Production canaries across generic `/v1`, Hermes `/hermes/v1`, and Memory `/memory/v1` in streaming and non-streaming modes passed, with a separate live Memory JSON Schema check.
- The 2026-08-12 Hermes canary used M365 model-specific `context_length=80000` and `proactive_prune_tokens=41000`, with global `compression.threshold_tokens` unset. A real oneshot terminal-tool turn completed two API calls, and Hermes' native `ContextCompressor` confirmed no prune at 40999 and deterministic old-tool-result pruning at 41000. Real tool-heavy long-task evidence on 2026-08-13 later showed that 80K is too permissive for the `128000 UTF-16` transport policy: even after repeated compression to roughly 49K–52K rough tokens, new tool results could regrow the outbound request past the transport limit until all three compression recoveries were consumed. The current Production baseline is therefore `context_length=64000`, `proactive_prune_tokens=41000`, `max_attempts=3`, and `protect_last_n=20`; the 80K canary remains historical evidence of a previously usable looser setting, not the current recommendation.
- Traditional Chinese retain, recall, and reflect have passed live PoC validation. Contradictory old facts can briefly coexist with newer facts immediately after retain, but consolidation can replace the stale observation with a correct current state; production must therefore monitor pending and failed consolidation.
- Hermes and Hindsight may share one Microsoft 365 account but also share account-level throughput. New Memory jobs are admitted cooperatively: both legacy `/v1/chat/completions` traffic and the dedicated `/hermes/v1/*` surface count as interactive priority, Memory waits in FIFO order, and Memory already in flight is not interrupted.
- 429 and backoff behavior is verified with deterministic local tests. Live Microsoft accounts are not intentionally flooded to discover throttling thresholds.
