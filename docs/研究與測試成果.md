# 研究與測試成果

本文件整理目前公開 `main` 的實作與驗證結論，供實作者理解行為邊界；內容不含私人路徑、帳號識別、原始封包或內部治理資訊。

## 1. 文字輸入與 checkpoint 行為

- `128000` UTF-16 units 是官方 Web editor 的已驗證相容邊界：`128000` 可送出，`128001` 由 UI 阻擋。
- 這個數值**不是**目前已證明的 ChatHub backend 硬上限。較大的 direct ChatHub 輸入曾成功通過 transport 並取得 backend acceptance。
- 對外公開時，最安全的產品說法是：
  - `128000` 為 Web-compatible policy。
  - 更大的輸入可能被接受，但處理時間會明顯增加，也可能因排程或模型執行時間而 timeout。
- Conversation reuse 應依 strict hash-prefix / checkpoint ordering 驗證：
  - 只有在舊 history 前綴完全一致時才沿用既有 Microsoft `ConversationId`。
  - 若上層 consumer 改寫了歷史訊息、壓縮了舊內容，或 tool result 內容不同，就應安全地建立新 conversation，而不是做 fuzzy match。

## 2. Private / Temporary Chat 與記憶邊界

- `disableMemory=1` 是目前最重要的 no-ordinary-history transport control。
- 同一個 Private / Temporary conversation 內，Microsoft 仍可能保留短期 continuation state；這不等於長期 memory。
- 因此合理責任分工是：

```text
長期 history / memory / compression
→ 由上層 consumer 管理

短期 ConversationId / SessionId / file continuation
→ 由 Sidecar 只在當前流程內短暫使用
```

- 重新建立 ChatHub WebSocket 時，應再次套用 `disableMemory=1`；不能因為沿用同一個 `ConversationId` 就假設 private policy 仍自動有效。

## 3. Files、圖片與多模態行為

### 一般文件

- 一般文件不是把原始 bytes 直接塞進 ChatHub `message.text`。
- 目前可公開描述的實作方向是：

```text
Graph createUploadSession
→ SharePoint / OneDrive upload
→ file identity / annotation
→ ChatHub grounding
```

- 文件上傳與聊天 no-history 是兩個不同問題。即使使用 `disableMemory=1`，文件仍可能在 Microsoft 端建立 staging copy。
- 同一 turn 的 active attachments 以 3 個為已驗證上限；文件與圖片共用這個配額。

### 圖片與 Vision

- 圖片與一般文件走不同 transport。
- Vision 已有單圖、多圖、不同圖片格式的正向驗證；圖片內容會真正進入模型處理，而不是只經過本地假解析。
- 圖片路徑不應強迫共用文件的 Graph / SharePoint upload flow。

## 4. Bing、caller tools 與工具協調

- `tools` schema 的存在，本身不代表 Microsoft native Bing 一定會被關閉。
- 已觀察到的主要風險是 tool-routing prompt wording：
  - 若 prompt 把模型限制成「只能先處理 caller tool」，native Bing 可能被壓制。
  - 若 prompt 明確保留 Microsoft native Bing / citations / grounding，則 Bing 與 caller tool 可以在同一 turn 共存。
- 這代表問題更像是 prompt / routing contract，而不是 upstream 完全不支援 coexistence。

## 5. Code Interpreter 與產出檔案

- `Code Interpreter` 可在上游真正執行 Python，並回傳 output-file metadata。
- 瀏覽器中可點擊的 `blob:` URL 只是前端表現層，不是可直接交給 API 呼叫端的上游檔案 identity。
- Sidecar 已完成下列物化路徑：

```text
以已登入身分擷取上游檔案
→ 本機私有儲存區
→ 短期 capability URL
```

- capability URL 的持有者即可下載，因此必須視同短期憑證保護；上游擷取、完整性或容量檢查失敗時會失敗關閉。

## 6. SignalR terminal semantics

- ChatHub stream 的 partial update 不能單獨當作成功完成。
- 公開 API 相容層應以 terminal completion 為準，再決定是否輸出最終 `finish_reason`、usage 與 `data: [DONE]`。
- 對 SSE consumer 而言，重點不是只看到零散 delta，而是：
  - partial deltas 順序正確；
  - terminal completion 到達；
  - 最後補上 `[DONE]`。

## 7. MCP 與 Hermes 呼叫端相容性

- `/v1/mcp`、`/v1/mcp/sse` 與 `/v1/mcp/message` 均已掛載；第一條使用 Streamable HTTP，後兩條是成對的舊版 SSE 傳輸。
- 路由已掛載不等於每個呼叫端都能直接互通；實際相容性仍取決於呼叫端支援的傳輸與 MCP 初始化流程。
- 對 Hermes 類呼叫端而言，核心相容路徑仍是 `POST /v1/chat/completions`。
- 文字、SSE 串流、單一呼叫端工具、視覺輸入、一般續接與短期產出檔案下載已有正向證據；大型工具結果、同一輪多個呼叫端工具及原生 Bing 混用仍有明確邊界。
