# 部署與反向代理 / Deployment and Reverse Proxy

## 中文

### 長任務 timeout 原則

M365-Copilot2API 的 `chatTimeoutSeconds` 控制請求進入 ChatHub 後，Sidecar 願意等待聊天完成的時間。帳號級 interactive admission 啟用後，請求在進入 ChatHub 前還可能等待最多 `interactiveQueueTimeoutSeconds`。若前方還有 Synology Reverse Proxy、Nginx、Cloudflare 或其他 proxy，其讀取/傳送 timeout 必須 **大於 interactive queue timeout 與聊天 timeout 的總和**；否則合法排隊或仍在正常處理的請求會先被外層 proxy 切斷。

建議關係：

```text
反向代理 read/send timeout
> Hermes stale/request timeout
> M365 interactiveQueueTimeoutSeconds + chatTimeoutSeconds
> 預期最長模型處理時間
```

例如 `interactiveQueueTimeoutSeconds = 300`、`chatTimeoutSeconds = 1800` 時，Sidecar 的 interactive request 最長生命週期約為 `2100` 秒；反向代理 read/send timeout 應再高於此值，例如約 `2400` 秒，保留 Hermes 與連線收尾餘裕。這是部署範例，不是固定產品規格；若日後調整 queue、Sidecar 或 caller timeout，整條鏈都必須同步檢查。

`proxy_connect_timeout` 只控制建立到 Sidecar 的連線，不需要因模型推理時間而同步拉到 1800 秒。真正會切斷長 reasoning request 的通常是 `proxy_read_timeout`；`proxy_send_timeout` 也應提供足夠餘裕。

Hermes 還有自己的 stream/non-stream stale detector 與 request timeout。以目前 `300 + 1800 = 2100` 秒的 Sidecar interactive 上限為例，可使用 Hermes stale `2200` 秒、request timeout `2300` 秒，以及約 `2400` 秒的 reverse proxy read/send timeout。重點不是固定數字，而是**不要讓 Hermes 或 proxy 比 M365 更早切斷仍在合法排隊或正常 reasoning 的 request**；任何一層調整後都要重新檢查整條 timeout chain。

### 設定來源與重建

設定不是單純「環境變數永遠優先」或「設定檔永遠優先」，而是依欄位類型處理：

- `chatTimeoutSeconds`、`imageTimeoutSeconds` 等一般執行設定：環境變數只提供啟動預設值；`settings.json` 有保存該欄位時，以保存值為準。因此已保存 `1800` 不會被 `M365_CHAT_TIMEOUT_SECONDS=120` 重新蓋回去。
- `listenAddress`、token/session 路徑、OAuth、outbound proxy 等「重新啟動後生效」欄位：明確由 Compose/systemd 等外部注入的 process environment 優先。只有環境變數不存在時，Sidecar 才會把 `settings.json` 的保存值注入啟動環境。
- `M365_MAX_TOOL_CALLS_PER_TURN` 與 `M365_MAX_TOOL_ROUNDS` 是直接 runtime override；只要 process environment 存在，就會蓋過 UI 保存值。

管理 API/UI 會分開顯示「已保存值」、「目前生效值」與來源（`file` / `env` / `default`）。若欄位被外部環境變數鎖定，UI 會明確標示，避免使用者誤以為重新啟動後就會套用另一個保存值。

`settings.json` 是正式備份／還原的一部分。新主機、清空 data directory 或只還原部分資料時，不能假設舊的 1800 秒 timeout 仍存在；可重建的 Production deployment 設定也必須提供符合長任務需求的安全預設。對需要最長約 30 分鐘推理的部署，`1800` 秒是合理的 ChatHub 等待基準；外層 reverse proxy 與 caller timeout 必須再加上 interactive queue budget 與收尾餘裕。

安全偵錯摘要也屬於持久化資料。明確設定 `M365_DEBUG_LOG` 時會使用該路徑；未設定時，預設為 `settings.json` 同一目錄下的 `debug-logs.json`。因此使用 `M365_DATA_DIR=/data` 的容器部署會自動寫入 `/data/debug-logs.json`，不依賴通常可能是唯讀的應用程式工作目錄。請將該目錄掛載為可寫且持久化；檔案以 `0600` 權限原子寫入，內容仍受既有遮蔽與容量／TTL 政策限制。

### NAS Production 自動部署

repo 提供 `scripts/deploy-nas-production.sh`，用來把已驗證的 Linux/amd64 binary 部署到目前 Synology Production。腳本刻意把本次實際踩到的兩個故障模式納入流程：

- recreate 後不會立刻以單次 HTTP probe 判定失敗，而是最多等待 `M365_READY_TIMEOUT`（預設 90 秒），同時確認容器仍為 running 且 Sidecar 已開始回 HTTP。
- rollback 不會直接覆寫仍在執行中的 binary；會先停止 M365 service，再以 temp + rename 還原舊 binary，避免 `Text file busy`。

腳本需要執行端已有 `home-nas-agent` SSH 連線，以及以 `LOCAL_NAS_SHARED_PASSWORD` 安全注入的 NAS 管理密碼。密碼只送進遠端 `sudo -S` stdin，不應出現在命令列、log 或 repo。

範例：

```bash
LOCAL_NAS_SHARED_PASSWORD='...' \
  bash scripts/deploy-nas-production.sh \
  --binary /tmp/m365-native \
  --sha256 '<release-binary-sha256>' \
  --commit '<release-commit-sha>'
```

部署順序為：驗證 candidate SHA → remote staging → 建立暫時 rollback backup → 原子替換 binary → 只調整 Production compose 的 chat/image timeout 為 1800 → force-recreate 單一 `m365` service → readiness 輪詢 → 驗證 binary SHA/commit、settings migration、`/v1/models` 與 `/memory/v1/models`。部署成功後，暫時 rollback backup 會自動刪除；rollback 成功後也會刪除。只有 rollback 本身失敗時才保留 backup 供人工復原。

上面是部署腳本本身的生命週期。如果某次發佈還要求 **Production live qualification 才能視為完成**，不要讓「部署命令成功」先於驗收撤掉唯一復原點。此時應在部署前另外建立可驗證、獨立保留的 recovery snapshot（至少涵蓋 binary、compose 與 `settings.json`），記錄 hash 與舊 runtime identity，並保留到：部署 identity 讀回 → 必要的 generic/Hermes/Hindsight live canary → final health/invariance readback 全部通過。只有 qualification 成功後才 cleanup snapshot；任一 gate 失敗則使用固定的舊 identity 回滾並再次讀回健康狀態。

### Synology Reverse Proxy

DSM Reverse Proxy 的預設 read/send timeout 可能只有 60 秒。長 reasoning 任務若固定約一分鐘出現 Synology HTML 504，先檢查此設定，而不是把它誤判成模型或 Microsoft 端 timeout。

以 Nginx 語意表示，長任務設定可類似：

```nginx
proxy_connect_timeout 60;
proxy_read_timeout 2400;
proxy_send_timeout 2400;
```

請優先透過 DSM 支援的 Reverse Proxy 設定介面/API 修改，不要只直接改 generated Nginx `.conf`；DSM 重新產生設定時，直接修改的檔案可能被覆寫。變更後應驗證有效設定、重新載入結果，以及公開 HTTPS route 的實際長連線行為。

### 與 128K 文字政策的關係

Proxy timeout 與 `textInputLimitUTF16` 是兩個獨立限制：

- timeout 解決「模型處理很久但連線被外層切斷」。
- UTF-16 policy 解決「呼叫端文字超過 Web 相容政策」。
- Hermes 等 Agent 還應在更前面以自己的 token context/compression 機制控制歷史大小。

請勿藉由單純增加 timeout 來解決 oversized context，也不要藉由降低文字上限來掩蓋 proxy 504。

## English

### Long-running request timeout rule

`chatTimeoutSeconds` controls how long M365-Copilot2API waits after a request enters ChatHub. Account-level interactive admission can additionally hold a request for up to `interactiveQueueTimeoutSeconds` before that upstream work starts. If Synology Reverse Proxy, Nginx, Cloudflare, or another proxy sits in front of the Sidecar, its read/send timeout must be **greater than the interactive queue timeout plus the chat timeout**. Otherwise valid queued or still-processing requests can be cut off first.

Recommended relationship:

```text
reverse-proxy read/send timeout
> Hermes stale/request timeout
> M365 interactiveQueueTimeoutSeconds + chatTimeoutSeconds
> expected longest model processing time
```

For example, `interactiveQueueTimeoutSeconds = 300` plus `chatTimeoutSeconds = 1800` gives an interactive request lifetime of about `2100` seconds. A reverse-proxy read/send timeout around `2400` seconds leaves room for Hermes and connection completion. This is a deployment example, not a fixed product specification. Re-check the entire chain whenever queue, Sidecar, or caller timeouts change.

`proxy_connect_timeout` only governs establishing the connection to the Sidecar and normally does not need to match model reasoning duration. `proxy_read_timeout` is the common cause of long reasoning requests being cut off; `proxy_send_timeout` should also leave adequate margin.

Hermes has its own streaming/non-streaming stale detectors and request timeout. With the current `300 + 1800 = 2100` second Sidecar interactive maximum, one correctness-first profile uses Hermes stale timeouts of `2200` seconds, a request timeout of `2300` seconds, and a reverse-proxy timeout around `2400` seconds. The exact numbers are less important than the invariant: **Hermes and the proxy must not terminate a request while it is still legitimately queued or reasoning inside M365**. Re-check the entire timeout chain whenever any layer changes.

### Configuration sources and rebuilds

Precedence depends on the setting class rather than one global rule:

- General runtime settings such as `chatTimeoutSeconds` and `imageTimeoutSeconds`: environment variables seed startup defaults, then persisted fields from `settings.json` override those defaults. A persisted value of `1800` therefore remains effective even if `M365_CHAT_TIMEOUT_SECONDS=120` exists as a deployment default.
- Restart-required settings such as listen address, token/session paths, OAuth, and outbound proxy: an explicitly supplied process environment value from Compose/systemd wins. The Sidecar injects the persisted value into the startup environment only when that environment variable is absent.
- `M365_MAX_TOOL_CALLS_PER_TURN` and `M365_MAX_TOOL_ROUNDS` are direct runtime overrides; when present, they override the value saved by the admin UI.

The admin API/UI exposes the saved value, current effective value, and source (`file`, `env`, or `default`). Externally environment-locked fields are marked clearly so a saved UI value is not mistaken for the value that will become active after restart.

Treat `settings.json` as part of the qualified backup/restore set. A new host, an empty data directory, or a partial restore must not assume the previous 1800-second policy still exists. Reproducible Production deployment configuration should also carry a safe default for the intended workload. For deployments expected to support reasoning tasks up to roughly 30 minutes, 1800 seconds is a reasonable ChatHub waiting baseline. Caller and reverse-proxy timeouts must additionally include the interactive queue budget and completion margin.

Redacted diagnostic summaries are durable state as well. An explicit `M365_DEBUG_LOG` path remains authoritative; otherwise the default is `debug-logs.json` beside `settings.json`. A container using `M365_DATA_DIR=/data` therefore writes `/data/debug-logs.json` instead of depending on an application working directory that may be read-only. Mount that directory writable and persistent. The file is atomically written with mode `0600` and remains subject to the existing redaction, size, and TTL policies.

### Automated NAS Production deployment

The repository provides `scripts/deploy-nas-production.sh` for deploying a qualified Linux/amd64 binary to the current Synology Production environment. It explicitly handles the two failure modes observed during the first hardened deployment:

- Readiness is polled for up to `M365_READY_TIMEOUT` (90 seconds by default) instead of treating one immediate post-recreate HTTP failure as a dead service.
- Rollback stops the M365 service before restoring the executable and uses a temporary file plus rename for binary restoration, avoiding `Text file busy`.

The runner must already have the `home-nas-agent` SSH target and a securely injected `LOCAL_NAS_SHARED_PASSWORD`. The password is sent only through stdin to remote `sudo -S`; it must not be placed in the repository, command line, or logs.

Example:

```bash
LOCAL_NAS_SHARED_PASSWORD='...' \
  bash scripts/deploy-nas-production.sh \
  --binary /tmp/m365-native \
  --sha256 '<release-binary-sha256>' \
  --commit '<release-commit-sha>'
```

The script verifies the candidate SHA, stages it remotely, creates a temporary rollback set, atomically replaces the binary, changes only the Production chat/image timeout values to 1800, force-recreates only the `m365` service, polls readiness, then verifies the deployed SHA/commit, settings migration, `/v1/models`, and `/memory/v1/models`. The temporary rollback backup is removed after a successful deployment or a successful rollback. It is retained only when rollback itself fails and manual recovery is required.

That is the lifecycle of the deployment script itself. When a release is not considered complete until **Production live qualification** also passes, do not let a successful deployment command remove the only recovery point before acceptance. Create a separately retained, verifiable recovery snapshot before deployment (at minimum the binary, compose file, and `settings.json`), record hashes and the previous runtime identity, and keep that snapshot through deployed-identity readback, the required generic/Hermes/Hindsight live canaries, and the final health/invariance readback. Clean it up only after qualification succeeds. If any gate fails, roll back to the pinned previous identity and independently re-read service health.

### Synology Reverse Proxy

DSM Reverse Proxy may default to a 60-second read/send timeout. If long reasoning tasks consistently return a Synology HTML 504 at roughly one minute, inspect this layer before attributing the failure to the model or Microsoft.

Equivalent Nginx semantics for a long-running deployment can look like:

```nginx
proxy_connect_timeout 60;
proxy_read_timeout 2400;
proxy_send_timeout 2400;
```

Prefer DSM's supported Reverse Proxy UI/API over directly editing generated Nginx `.conf` files; generated files may be overwritten. After changing the setting, verify the effective configuration, reload result, and actual long-lived behavior through the public HTTPS route.

### Relationship to the 128K text policy

Proxy timeout and `textInputLimitUTF16` are independent limits. Timeout tuning prevents an outer proxy from terminating legitimate long-running work; the UTF-16 policy bounds caller text for Web compatibility. Agents such as Hermes should manage history even earlier using their own token context/compression mechanism.
